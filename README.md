# Zeitgeist

Zeitgeist is a public trend aggregation dashboard that collects internet and
sports signals from verified APIs, stores normalized snapshots in Postgres, and
serves a category dashboard from stored data. User-facing pages do not call
external source APIs or Gemini during page loads.

The current product uses a Django REST Framework backend, a Next.js frontend,
scheduled Cloud Run ingestion, and Terraform-managed Google Cloud
infrastructure.

## Current Status

Phase 1 and Phase 2 are complete. The app has been deployed publicly at
`https://dailyzeitgeist.xyz` with a production HTTPS load balancer, managed TLS,
same-origin API routing under `/api/v1`, Cloud Armor on the API backend, Cloud
Run restricted ingress, scheduled ingestion, and Gemini category summaries.

Current active categories and sources:

| Category | Source |
|---|---|
| Tech | Hacker News, DEV |
| News | New York Times Most Popular |
| Gaming | RAWG |
| Sports | Football-Data, Cricket Data |

Current user-facing features:

- Public dashboard and `/category/[slug]` detail pages.
- Stored trend data from Postgres, not direct browser calls to source APIs.
- Source-specific trend cards, including football and cricket match cards for Sports.
- Sports category source tabs without an "All" option that mixes different sports.
- Category summaries generated by Gemini during ingestion and stored in Postgres.
- Source-specific Sports summaries for cricket and football on the Sports page.
- Email/password signup and signin using Django session authentication.
- CSRF-protected browser API calls with production same-origin cookies.
- SMTP one-time-password verification for registration.
- Forgot-password flow using the same OTP pattern.
- Saved category preferences for signed-in users.

## Architecture

| Layer | Technology |
|---|---|
| Backend | Django 5.1 + Django REST Framework |
| Frontend | Next.js App Router + TypeScript |
| Database | Postgres 16 on Cloud SQL |
| Batch ingestion | Cloud Run Job triggered by Cloud Scheduler |
| AI summaries | Vertex AI / Google Gen AI SDK with Gemini |
| Edge routing | External HTTPS Load Balancer with managed SSL |
| Edge protection | Cloud Armor attached to the API backend service |
| Secrets | GCP Secret Manager |
| Images | Artifact Registry |
| Infrastructure | Terraform |
| CI/CD | GitHub Actions with Workload Identity Federation |

Production request flow:

```text
Browser
  -> dailyzeitgeist.xyz
  -> HTTPS Load Balancer
      -> /api/* -> Cloud Armor -> Cloud Run API
      -> everything else -> Cloud Run Frontend
```

The frontend does not call the API by a private Cloud Run service URL. Browser
requests use same-origin `/api/v1`; server-side Next.js requests use
`SERVER_API_BASE_URL=https://dailyzeitgeist.xyz/api/v1`. Both paths go back
through the load balancer. Direct public access to raw `run.app` service URLs is
blocked by Cloud Run ingress settings.

Runtime ownership:

- Terraform owns stable infrastructure: Cloud SQL, Cloud Run service/job shells,
  Scheduler, Artifact Registry, Secret Manager containers, IAM, load balancer,
  Cloud Armor, and scaling.
- GitHub Actions CD owns runtime images, migrations, seed data, and Cloud Run
  runtime environment/secret attachment.
- Secret values are never stored in Terraform. Terraform creates secret
  containers only; `infra\secrets.bat` or CD supplies values.

## Local Development

Start Postgres:

```cmd
docker compose up -d
```

Set up the backend:

```cmd
cd backend
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements-dev.txt
copy .env.example .env
python manage.py migrate
python manage.py seed_categories
python manage.py runserver localhost:8000
```

Run ingestion locally:

```powershell
cd backend
$env:DJANGO_SETTINGS_MODULE="config.settings.development"
python run_job.py
```

Run the frontend:

```cmd
cd frontend
npm install
npm run dev
```

Local URLs:

- Frontend: `http://localhost:3000`
- Backend health: `http://localhost:8000/api/v1/health/`
- Dashboard API: `http://localhost:8000/api/v1/dashboard/`
- Django admin: `http://localhost:8000/admin/`

For local SMTP and AI summary testing, fill the relevant values in
`backend\.env`. Do not commit that file.

```text
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=smtp.example.com
EMAIL_PORT=587
EMAIL_HOST_USER=your-email@example.com
EMAIL_HOST_PASSWORD=replace-me
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
EMAIL_VERIFICATION_OTP_TTL_MINUTES=10
EMAIL_VERIFICATION_MAX_ATTEMPTS=5
EMAIL_VERIFICATION_RESEND_COOLDOWN_SECONDS=60
AUTH_RATE_LIMIT_WINDOW_SECONDS=60
AUTH_RATE_LIMIT_IP_REQUESTS=30
AUTH_RATE_LIMIT_EMAIL_REQUESTS=10
AI_SUMMARIES_ENABLED=true
GOOGLE_CLOUD_PROJECT=replace-me
GOOGLE_CLOUD_LOCATION=global
GOOGLE_GENAI_USE_ENTERPRISE=True
GEMINI_MODEL=gemini-3.5-flash
```

`DEFAULT_FROM_EMAIL` is derived in code as `Zeitgeist <EMAIL_HOST_USER>` unless
explicitly overridden.

## Testing

Backend:

```cmd
cd backend
python manage.py makemigrations --check --dry-run
python -m pytest --no-cov
python -m ruff check .
python -m mypy apps config
```

Frontend:

```cmd
cd frontend
npm run typecheck
npm run lint
npm run build
```

Terraform:

```cmd
cd infra
terraform fmt -check -recursive
terraform validate
terraform plan
```

Do not run `terraform apply` until the plan has been reviewed.

## Cloud Bootstrap After `terraform destroy`

Use this order after recreating the project infrastructure:

```cmd
cd E:\Coding-practice\Projects\zeitgeist\infra
terraform apply
```

Then populate secrets and update non-secret runtime config:

```cmd
cd E:\Coding-practice\Projects\zeitgeist
infra\secrets.bat
cd infra
terraform apply
```

Finally push to `main` so CD deploys the real images, runs migrations, seeds
categories, and attaches runtime secrets:

```cmd
git push origin main
```

Production API host, CORS, and CSRF values are computed by `.github/workflows/cd.yml`
from the custom domain and Cloud Run service URLs. The browser API base remains
same-origin `/api/v1`.

## Manual Ingestion

Run this to refresh production dashboard data manually:

```powershell
gcloud run jobs execute zeitgeist-ingest --region us-central1 --project zeitgeist-499322 --wait
```

## Cost Controls and Teardown

For short breaks, pause scheduled ingestion and scale services down. For a full
shutdown, prefer `terraform destroy` from `infra` after confirming you no longer
need the Cloud SQL data.

Useful checks:

```powershell
gcloud run services list --region us-central1 --project zeitgeist-499322
gcloud run jobs list --region us-central1 --project zeitgeist-499322
gcloud sql instances list --project zeitgeist-499322
gcloud scheduler jobs list --location us-central1 --project zeitgeist-499322
```

## Source Verification Rule

Before adding a source:

1. Confirm auth/key requirements and free-tier limits.
2. Fetch live sample data.
3. Confirm response fields support a useful UI.
4. Add the adapter, seed mapping, tests, docs, and secrets only after verification.

Deferred sources and alternate auth/email providers are not part of the current
implementation and should not be added back without a live verification pass.
